### What the generic checker compares (`chk_gen.py`)
For every section it disassembles the catalogue extent (including `.HOODLUM` bodies) and checks:
- every `slot N (+0xM) of vtable 0xV` claim: `M == 4N` and `[V + 4N] == function` (239 claims in AI pass 2, all correct);
- constant returns of tiny functions (`mov eax, imm` / `xor eax,eax` / `or eax,-1` / `mov al, imm` / `xor al,al` / `fld [k]`):
  241 integer returns and 11 ST0 returns in AI pass 2, all correct; 51 "AL only / upper EAX bits unchanged" claims, all
  really write AL only;
- every `` `ret N` `` claim against the function's `ret` immediates (flags were only callee descriptions);
- every code address in the text: an instruction boundary when inside the function, otherwise a call/jmp target or operand
  of the function or of its small callees (two levels), or a caller (catalog/callgraph.csv);
- every data address: an operand of the function or callees, or a vtable containing the function;
- every `+0xNN` field offset: used as a displacement or immediate by the function or its small callees;
- every `0xA in 0xF` cross-reference claim: A lies inside F and the instruction covering A references the cited global.
- Shape check: all 307 sections whose first line says "scalar deleting destructor" really `test [esp+..], 1` and `ret 4`
  (19 more mention a scalar deleting dtor only as evidence: thunks, deviation notes).

All residual flags (about 400 across populations) were read by hand: they are layout descriptions (`+0x50 u8 hitLevel[5]`),
neighbour/sibling references ("same as 0x4ac720", "users 0x629920"), callee conventions (`0x632C70 ... ret 0xC`), range ends
cited inclusively, and .HOODLUM addresses outside the catalogue extent (0x43C190). None changes behaviour.

### "Same as 0xX" claims (`chk_same.py`)
140 claims in UNK/AI pass 2 + 5 in REST, compared instruction by instruction (branch targets normalised): 52 byte-identical,
30 identical except constants, 63 differ. Every differing pair was read: the text names the difference each time (pool
address and division magic, element size, vtable, reference slot offsets, "not relocated", "Prologue as" with different
frame size). Examples verified: the 20-function `CPool<T>` scalar-deleting-dtor family 0x5512F0..0x5518F0, 0x5D9450,
0x5D94B0, 0x5D9510, 0x731C20 (identical behaviour; the RW four call `0x8214BD` directly instead of the `0x8213AE` thunk,
both are `_free`); 0x492F60 vs 0x46A610 (same store of 0x859DC4, the latter through a .HOODLUM detour).

## 2. Findings

### 2.1 Initialiser table rows: what was re-derived
For every row: the `__xc` slot holds the function (table 0x8A4004..0x8A5A7C); the bytes are exactly
`fld a; (fmul|fdiv|fsub) b [; fdivr c]; fstp g; ret` with the claimed operand addresses in the claimed order and target g;
every constant operand's image value equals the claimed value; "initial .data value" operands are in initialised data and
not written by an earlier initialiser; "set by an earlier initialiser" operands are written by an initialiser in an earlier
slot and the derived value matches; ".bss, still 0.0" operands are zero in the image and no initialiser writes them; the f32
result was recomputed in `__xc` slot order with both a 53-bit and a 24-bit model, and both agree with the claimed value in all
1,416 rows (no row needs a DIFFERS note).

Init-order finding (resolves the WORKLOG question "0x84CED0/0x84CF80/0x84D0F0 read .bss nobody wrote yet"): there is no
order bug. The .bss operands 0xB6B9D4, 0xB6B9D8 (and 0xB6B9CC, 0xB6B9D0) are zero-initialised floats: gta-reversed
`AEVehicleAudioEntity.h:442/450` gives `VolMin{0.f}` at 0xB6B9D8 and `VolMax{0.f}` at 0xB6B9D4 (lines 387/398 for the other
two). MSVC put the zero-initialised members in .bss, so reading 0.0 there is the intended value.

### 2.3 Systematic generator errors
1. AI pass-2 scalar-deleting-dtor generator with an inlined pool `operator delete`: it always writes "event pool /
   ms_pEventPool / CEvent::operator delete", whatever pool address the bytes load. Every section of this shape was scanned
   (73 lines mention the event pool): 63 really use 0xB744AC and are right; the 10 attractor sections listed in 2.2 use
   0xB744C4 and are wrong. No other pool address is mislabelled in this shape (scan of all `0xB744xx` pool labels in
   docs/re/specs; the remaining hits are lists in SCRIPT files where both pools are named correctly).
2. RE-SPEC-UNK "readers" column: raw byte search for the 4-byte address without decoding, so it can report misaligned
   matches. Affected rows: 0x850AC0, 0x854A00, 0x851600, 0x84D9B0 (all corrected). It also cannot see readers that reach a
   global through `base + offset` of a neighbouring symbol; such readers would be missed by any address scan. Treat
   "dead store" as "no direct absolute reference".
3. `check_consts.py` false positives (tool, not specs): `0xG = value [0xK]` pairs the store target G with the value, and
   `+-0.1f [0xK]` is read as -0.1. All 10 current flags are this: CCam.md:997 (statics 0xB70100/0xB700FC, constants
   0x862F20 = 3.0f and 0x862F24 = 20.0f are right), VEH/_static-init-E.md:67, WEAPON/_static-init.md:23/29/33/45,
   RW/_static-init-p3.md:12 (RW-3, not audited), VEH/CPlane.md:173 (clamp is ±0.1: `fld [0x8D3408]` / `fchs` at
   0x6CA592-0x6CA5A0), VEH/CCarEnterExit.md:86 (gr label, see 2.2). The committed-at-start run also flagged
   CAM/CCamera.md:461 (`q = 3.0 [0x858B3C] (-3.0 [0x859024])`, correct); that line has since been reworded in the working tree.

No generator was found wrong for: constant-return getters, GetTaskType/GetEventType, float getters, vtable slot claims,
scalar deleting dtors (flag test, operator delete target, complete-dtor target, `ret 4`), non-deleting dtors (vtable
stores), Clone (allocation size, ctor target, copied fields), thunks, header-constant initialisers, atexit registrations,
CPool families.

## 4. Confidence in the rest
- Initialiser tables (1,416 rows): every claim except "readers" is proven from the bytes; high confidence.
- Trivial generated sections (AI pass 2, UNK, REST): every address, slot, offset, return constant and `ret` claim was
  matched; the shapes are simple enough that this covers their whole behaviour. High confidence, with the caveat that
  textual names of globals were only checked where a name/address table exists (pools); other names come from gr/plugin-sdk.
- Larger never-executed sections (UNK-A/B, REST, hand-written): the checker proves that cited addresses, offsets and
  constants exist in the bytes, but not branch polarity, float operation order, loop bounds or signedness. For those the
  only evidence is the samples: 2 MINOR errors in 58 sections (≈3 %), both behaviour-neutral in practice, no WRONG. Ports
  should still re-read branch conditions and signedness from the bytes (L1/L2 parity covers this).
