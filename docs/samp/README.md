# SAMP-1 (static part): what the SA:MP client needs from gta_sa.exe

Goal: find out which gta_sa.exe 1.0 US functionality the SA:MP client depends on, so that an
"SA:MP-playable standalone" milestone can be scoped. The client in question is samp-rs, which reproduces
samp.dll 0.3.7-R4. The inventory is static only. Section 6 lists what the dynamic measurement still has to confirm.

Files (all generated by `docs/samp/samp_usage.py`, deterministic: two runs give byte-identical output):

| File | Content |
|---|---|
| `catalog/samp-usage.csv` | 1,199 rows, one per address/patch/field/opcode with its source `file:line` |
| `docs/samp/required-functions.csv` | one row per live catalogue function (15,486): direct?, which closure variants contain it, cut by samp? |
| `docs/samp/aggregates.json` | every number quoted below, plus the full lists (cuts, removed edges, features, opcodes, unresolved) |
| `docs/samp/samp_usage.py` | the generator: `.venv/bin/python -I docs/samp/samp_usage.py` (about 10 s, reads ~/samp-rs, never writes there) |

## 1. Inputs

* **samp-rs** `crates/samp-client/src/**/*.rs` (60 files): every hex literal and every `const` expression
  (`BASE + 0xC` is evaluated) whose value falls inside a gta_sa.exe section.
* **samp.dll patches** `~/samp-rs/docs/re/data/gta-patches-r4-annotated.csv`: 384 rows, which expand to 402
  address entries (rows that list several addresses are split).
* **Our catalogue**: `procedures.csv` (names, subsystem, state), `extents.csv` (body ranges, used to map an
  address inside a body to its function), `data-tables.csv` (vtables / function tables), global names
  (`tools/catalog/callgraph.py global_names`: gta-reversed + plugin-sdk), `callgraph.csv`, `rwsets.csv`,
  `script-commands.csv`, and plugin-sdk `VALIDATE_OFFSET` (4,142 field offsets) for struct fields. Vtable slot
  targets and the bytes at fall-through ends are read from `re/gta/1.0-US/gta_sa.exe`.

## 2. Method

### 2.1 samp-rs occurrences
* Comments are stripped. String literals are blanked, except those holding an x86 instruction (`naked_asm!`
  operands such as `"cmp dword ptr [esp], 0x59E8F9"`). `#[cfg(test)]` items are tracked: 18 addresses occur
  only in tests and get no row (they are counted in `aggregates.json`).
* Values dropped as not being addresses: 15 outside every game section (colours), 5 range bounds of
  plausibility checks (`(0x80_0000..=0x90_0000).contains(&vt)`), 1 BASS flag word, 1 constant that only
  serves as the base of derived constants (the derived addresses are listed). 622 distinct addresses remain.
* Location (`loc`): `fn-entry` (a catalogue entry), `fn-body` (inside a body, mapped through `extents.csv`),
  `code-unmapped` (code bytes outside every body; these are the indirect-jmp slots samp writes into padding),
  `vtable` / `vtable-slot` (inside a `data-tables.csv` vtable, slot target read from the exe), and
  `data:<section>` (global name taken from gta-reversed / plugin-sdk, `X+0xNN` for fields of a named global).
* Kind is decided from the statement that holds the address, plus every non-test use of the constant's name:
  * `call`: `transmute` to an `extern` fn type, the `call*/thiscall*/cdecl*` helpers, `Op::Call`, or `orig = const`.
  * `hook`: `hook_call`, `hook_jmp`, `retarget_branch`, `swap_pointer`, indirect-jmp installers, or a write
    through the patcher onto a vtable slot. Hook continuation/resume addresses (`*_RESUME`, `*_CONTINUE`,
    `resume = const`) and return-address tests in hook stubs also count as `hook`, because they pin the
    original code layout.
  * `patch-disable`: a NOP or RET write. `patch-modify`: other byte writes into code.
  * `global-read` / `global-write` (both access types land in `also`). `global-access` means an operand of a
    hook stub where reads and writes are not separated.
  * `code-compare`: the code address is compared against a value. Examples: a caller list, or the original
    vtable target used to pick a handler.
  * `patch-operand`: a value that sits in the same statement as a samp patch site, i.e. the expected original
    target or the global being relocated.
* An address that equals a samp.dll patch site takes that row's kind. Its `patch_rows` column links back to
  the CSV line. Nine addresses that the rules could not classify were decided by hand (`SRC_MANUAL` in the
  script, one reason each, e.g. `AudioEngine` is passed as `this`).

### 2.2 samp.dll patch rows
* Hook kinds (`hook-call`, `hook-jmp`, `hook-jmp-indirect`, `call-retarget`, and `pointer-redirect` into
  samp code) count as `hook`. `pointer-redirect` into samp data counts as `patch-modify` (relocated tables:
  sector grid, model stores, colour table, float operands).
* Each of the 156 NOP / byte / data rows was read against its `effect` text and classified by hand
  (`PATCH_MANUAL` in the script). `patch-disable` means a game feature is switched off; it carries a `feature`
  label. `patch-modify` means behaviour or a limit changed. `global-write` means a game variable is set.
  `dead` marks samp.dll dead code (never applied). `code-read` is the auth check that reads code bytes.
* For every row the replaced instruction's call target (`orig: call 0x…`) is recorded. For vtable slots, the
  function the slot held is recorded.

### 2.3 needs
`implement-1:1`: call, hook, patch-modify, global, code-compare, patch-operand, struct-field, scm-opcode.
`option-off`: patch-disable. `n/a`: dead patches, the auth code read, and one opcode declared but unused.
Result: 1,068 rows `implement-1:1`, 115 `option-off`, 16 `n/a`.

### 2.4 Struct fields and opcodes
* Struct fields come from two sources. (a) Offset constants documented with a `` `Class::member` `` and used
  in an addition. (b) Inline `var + 0xNN` in a read/write, with the class guessed from the variable name
  (`ped` → CPed and so on). The result is checked against plugin-sdk `VALIDATE_OFFSET` along the
  plugin-sdk base-class chain.
* SCM opcodes are the `pub mod op` constants in `script.rs` and `worldents.rs`. An opcode counts only if it
  is used outside tests. Each one is executed through `CRunningScript::ProcessOneCommand` (0x469EB0).

## 3. Closure rule

Direct set (A): every live catalogue function that one of the following points at:
* a `call`, `hook`, `patch-modify`, `patch-disable` (body site), `code-compare` or `patch-operand` row;
* the original callee of a hooked call site (`hooked-callee`);
* the function a hooked vtable slot held;
* the `ProcessCommands…` range function of every opcode used.

Transitive closure: depth-first over `callgraph.csv` edges of kind `call`, `tailcall`, `virtual`,
`virtual-override`, `indirect-ghidra`, `eh-unwind` and `fnref` (callbacks), restricted to live catalogue
functions (no `excluded`, no `X-*`). Added on top:
* **Fall-through edges** (8). A body range that ends exactly at another entry, without ret/jmp/int3, falls
  into it. Notable case: `Win::NOTSA_WinMain` falls into 0x7487cf, which gta-reversed names
  `Input::Initialise`. That address holds the rest of WinMain in 1.0 US. Without this edge, `CGame::Initialise`
  is unreachable.
* **Instantiated tables** (variants C/E/F/G). When a reached function references a `data-tables.csv` table
  (any access in `rwsets.csv`: constructors store the vptr, code loads a callback table), every function in
  that table becomes reachable. This stands in for the 2,791 unresolved virtual-call sites.

samp's disables shape the closure. 3.1 lists the cuts; 3.2 lists what was deliberately left out.

### 3.1 Cuts applied
* **Cut functions** (8): init-time entry patches (`ret` / `xor eax,eax; ret`). Their bodies never run, so
  they are neither roots nor traversed: `CStreaming::InitImageList`, `CStreaming::DeleteAllRwObjects`,
  `CHud::SetHelpMessage`, `CFileLoader::LoadPickup`, `CPlayerPed::FindWeaponLockOnTarget`,
  `FindNextWeaponLockOnTarget`, `CPopulation::AddPed`, `CAutomobile::ProcessFlyingCarStuff`.
* **Removed edges** (23): a NOPed call (init time, not a runtime toggle) removes the edge caller → callee,
  but only when that caller has exactly one call site of that callee. Examples: `CGame::Process` → `CReplay::Update`,
  `CTheCarGenerators::Process`, `CCutsceneMgr::Update`, `CPlantMgr::Update`, `CCarCtrl::GenerateRandomCars`,
  `CCoronas::DoSunAndMoon`; `Idle` → `CRealTimeShadowManager::Update`. The full list is in
  `aggregates.json/removed_call_edges`.
* **Moot containers**: a function that is direct only because it contains a disable site, and that nothing
  else reaches, is not a root. The only case is `CCarCtrl::GenerateRandomCars`: its plane NOP is moot,
  because the function itself is NOPed out of `CGame::Process`.

### 3.2 Not cut
* Runtime and temporary RET patches stay in the closure: input lock, `CClock::Update`, `SetStatValue`,
  `CCamera::Fade`, `RebuildPlayer`, `ClumpCollisionStreamRead` and `CVehicle::SetupRender`. The game still
  runs these functions in some states, or before the patch is applied.
* NOPed blocks that contain calls are not cut (rows 167, 188, 215/217, 205, 361): only single-call NOPs are
  modelled.

**Reading:** samp does not shrink the engine much. Static reachability keeps two thirds of the catalogue,
because samp keeps the full frame loop (`Idle` → `CGame::Process`, rendering, streaming, script engine, AI
tasks via instantiated vtables). samp's own disables make only 182 functions unreachable. The 5,061
functions outside E are skip *candidates*, not proven skips. Unresolved indirect calls (function-pointer
variables, `call reg`) can reach them, so the dynamic measurement (§6) decides.

### 4.3 Features samp switches off (55 labels, 60 patch entries) — what the milestone may skip
Ambient population (`CPopulation::AddPed`, seating peds in cars), random traffic, car generators, ambient planes,
interior ambient peds, IPL pickups, interior pickups, cutscenes (`CCutsceneMgr::Update`), replay, plant manager,
sun/moon coronas, real-time shadows (update and return), speed blur, idle camera, single-player help boxes,
HUD vehicle name, HUD vital stats, zone-name display, "Wasted" message, menu map rectangle, loading-screen
splash rectangle, startup logos/intro (+ `gGameState` 5/8 writes and the menu flags: **main menu skipped**),
video-mode aspect filter, re-init on focus regain, weapon lock-on, event facial expressions, peds reacting to aimed
guns, Pay'n'Spray check, `CVehicle::SetDriver` freebies, flying-car physics, BMX fire ignition, sniper/rocket
"fire failed" sounds, ambient gunfire audio, cell-phone model, player idle animations, player anim-block release,
train passenger block, `Interior_c::Exit` in group exit, one unidentified `CPlayerInfo::Process` task block,
`ClearPlayerWeaponMode` in `ClearWeaponTarget`, streaming mass RW deletion and deletion after death,
game image-list registration. Runtime toggles: keyboard/mouse input and `RsMouseSetPos` while samp's UI owns
input, the game clock while the HUD clock is off, stat changes, the camera fade at spawn, CJ clothes rebuild,
`ClumpCollisionStreamRead` during samp model loads, and `CVehicle::SetupRender` (made RET by a hook body).
Per-row list: `aggregates.json/disabled_features`.

**Not a memory patch, but also off in SA:MP:** the single-player story. samp serves its own `main.scm` /
`script.img` from samp.saa (samp-rs `docs/phase3/saa2-notes.md`), so missions never load. Saving and loading
are never offered, because the menu is skipped. Static reachability cannot show either of these: the script
engine and `CGenericGameStorage` stay in E.

## 5. Proposed "SA:MP-playable standalone" milestone scope
1. **Implement 1:1:** the E set, 10,425 functions. Order: the 317 direct functions first (all hook targets,
   call targets and patch containers), then the B set (6,037), which is what samp's entry points reach over
   resolved edges.
2. **samp mode options (F13):** one option per samp patch entry. That is 60 `option-off` entries
   (55 feature labels) plus 220 `patch-modify` entries. Pool/limit sizes (15), sector/store/colour/model-pointer
   relocations (the 707-site model-pointer move is one row), the CFont stack frame (15) and the aspect constants
   become engine limits/options, not byte patches.
3. **Engine API (SAMP-API):**
   * 103 hook points: 41 call-site hooks, 4 jmp hooks, 18 indirect jmps, 1 call retarget, 39 slot/pointer
     redirects;
   * the 157 hook rows in samp-rs, including continuation addresses and return-address tests that assume the
     original code layout. In a Rust engine these must become explicit callbacks with caller identity;
   * 96 called functions, 99 globals and 62 struct fields that must keep their meaning;
   * the opcode runner for 103 opcodes plus two custom-opcode slots.
4. **May skip (pending §6):** the 5,061 functions outside E, plus the 182 that only samp's cuts make
   unreachable. By subsystem (live total, then not in E): RW 1,149 of 1,815, UNK-game 1,406 of 2,242, AI 510,
   RENDER 256, WORLD 246, STREAM 240, VEH 196, AUDIO 189, POP 181, CORE 112, ANIM 102. The story content
   (missions, saves, menus) is a further candidate. It stays in E statically but is never entered under samp
   (§4.3).

## 6. Dynamic measurement still needed (the confirmation step)
Run the original 1.0 US with samp.dll 0.3.7-R4 on an open.mp server, using our own Wine prefix and headless
display. Record executed game functions: INF-10 coverage, i.e. drcov, or entry breakpoints on all 15,486
catalogue functions. Scenarios: boot → connect → class selection → spawn → on foot → vehicles (car, bike,
boat, plane, heli, train) → weapons and damage → death/respawn → interiors → objects/pickups/textdraws/
dialogs/3D labels → disconnect. Then:
* intersect the result with E. Executed ∖ E reveals closure misses (unresolved indirect calls), and
  E ∖ executed gives the real skip list. Both are needed per subsystem;
* confirm each `patch-disable` feature never runs (e.g. `CReplay::Update` and the car generators have zero hits),
  and that the runtime toggles behave as described;
* log the SCM commands executed by samp's own scripts (samp-rs's tracer already has `SAMP_TRACER_SCRIPTS`) to
  close the opcode list of §4.4;
* run the samp handlers: for each hook, check whether it calls the original function. This decides whether
  the 29 `hooked-callee` functions and the vtable slot originals need 1:1 behaviour or only an interface.
